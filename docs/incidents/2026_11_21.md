# 障害報告: MacのChromeからweb01のWebページにアクセスできない

## 概要

| 項目 | 内容 |
| --- | --- |
| 発生日時 | [YYYY-MM-DD HH:MM] |
| 発見したきっかけ | Phase 2の動作確認で、ChromeからNginxの初期ページを開こうとした |
| 症状 | Chromeで http://<web01のIP> を開くと ERR_ADDRESS_UNREACHABLE が表示される |
| 影響範囲 | MacのChromeのみ。Safari、ターミナルの curl からは正常にアクセスできた |
| 結論 | サーバー側は正常。macOSのローカルネットワーク制限によりChromeの通信がブロックされていた |

## 環境

- 作業端末: Apple Silicon Mac(macOS [バージョン])、Google Chrome [バージョン]
- サーバー: Multipassで作成した仮想マシン web01(Ubuntu 24.04 LTS)、Nginx

## 切り分け

サーバーに近い側から順に確認した。

| 順 | 確認内容 | コマンド・操作 | 結果 | 判断 |
| --- | --- | --- | --- | --- |
| 1 | web01の中でNginxが応答するか | `curl -I http://localhost` | 200 OK | Nginxは正常 |
| 2 | ファイアウォールがHTTPを許可しているか | `sudo ufw status` | Nginx HTTP が ALLOW | ufwは正常 |
| 3 | Macから仮想マシンまで届くか | Macのターミナルで `curl -I http://<web01のIP>` | 200 OK | ネットワークは正常 |
| 4 | ブラウザによる違いはあるか | Safariで同じURLを開く | 表示できた | Chrome固有の問題と判断 |
| 5 | Chromeのエラー内容 | 画面のエラーコードを確認 | ERR_ADDRESS_UNREACHABLE | 公式情報・既知の事例を調査 |

## 原因

macOS Sequoia以降の「ローカルネットワーク」のプライバシー設定により、Chromeから同じネットワーク上の機器(仮想マシン)への通信がブロックされていた。

- ターミナルから実行したコマンドとSafariはこの制限の対象外のため、正常にアクセスできた
- ネットワーク機器メーカーの技術記事で、この制限によりChrome系ブラウザで ERR_ADDRESS_UNREACHABLE が出ることを確認した
- 設定画面の一覧に、同じ名前の「Google Chrome」が複数登録されていた。Chromeの更新のたびに別アプリとして登録される、という既知の事例と一致する。どの項目が現在のChromeか区別できず、許可しても反映されない状態だったと考えられる

## 対応

| 順 | 対応 | 結果 |
| --- | --- | --- |
| 1 | 「ローカルネットワーク」でChromeを許可し、Chromeを再起動 | 改善せず |
| 2 | 一覧のGoogle Chromeをすべてオンにし、Chromeを再起動 | 改善せず |
| 3 | [すべてオフにしてから許可を出し直す(実施した場合)] | [結果] |
| 4 | 動作確認にはSafariを使い、作業を継続 | 確認できた |

- システム保護(SIP)を無効にして設定ファイルを削除する方法も報告されていたが、Mac全体の安全性に関わるため実施しなかった

## 再発防止・今後の対応

- Webページの動作確認は、Safariとターミナルの curl で行う
- Chromeでアクセスできない場合は、まず curl とSafariで確認し、サーバー側かクライアント側かを切り分ける
- macOSの更新で設定画面から項目を削除できるようになったら、重複したChromeの項目を整理して再確認する

## 学び

- サーバーに近い側から順に確かめることで、サーバー側は正常で、クライアント(ブラウザ)側の問題だと特定できた
- エラーコード(ERR_ADDRESS_UNREACHABLE)を手がかりに、メーカーの技術記事などの情報を調べて原因を確定できた
- 「サーバーに届かない」原因は、サーバーやネットワークだけでなく、利用者側の端末の設定にもある
